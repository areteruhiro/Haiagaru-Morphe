# Kyodemoのワッチョイ部分検索の調査（開発中）

## 実装目標

ChMateで未取得の投稿も含め、Kyodemo全体からワッチョイ前半4桁／後半4桁を検索する。サイトに過度な負担をかけない。取得済みログだけの検索では目標達成としない。

## 確認できた事実

- `bs=hi&k=ID%3Anr7x80QOM` はエッヂ板でレスを返す。
- `bs=hi&k=-Kuom`、ワイルドカード付きの候補はHTTP 400と「IDを指定してください」を返す。
- `L20 abcd-Kuom`や`L20 -Kuom`はHTTP 200になるが「IDが見つかりませんでした」。部分一致への対応を証明する結果ではない。
- 公開の共通JavaScriptは検索フォームの送信、画面操作、取得結果の挿入を担当しており、サーバー側の検索実装は含まれない。
- 公開の全体検索フォームには「スレッド名」「板名」があり、公開の説明で全掲示板ワッチョイ部分検索APIは確認できない。
- robots.txtは一般クローラーに10秒間隔を指定し、検索クエリ付き板URLや一部板のクロールを制限している。全板の自動収集による独自索引作成を、低負荷な実装と見なさない。

## 次の検証

実際に結果が存在する完全なワッチョイを基準に、前半・後半の候補条件で同じ投稿が返るか比較する必要がある。HTTP 200だけでは成功扱いにしない。検索範囲（単一板／全体、現行／過去ログ）も独立して確認する。

`scripts/InspectKyodemoSuffixSearch.ps1` は公開ページの応答を保存する調査用。前半は `-Prefix abcd`、完全なワッチョイは `-Wacchoi 'L20 abcd-EFGH'` で指定する。リクエストは直列で最低10秒間隔、403／429／503または通信失敗で停止し、自動再試行しない。サイトの制限解除や全体検索を実現するものではない。

## 未完了事項

### 非公式のページ内取得経路

公開ページ内の返信展開リンク `/sdemo/r/android/1792102288/1?tk&fetch=t` は1への返信（5番、`ｵｲｺﾗﾐﾈｵ MMbb-sEDE`）を返した。通常ページ以外で投稿が取得できることは確認できたが、この処理はアンカーで参照される返信の取得であり、全投稿や全掲示板の部分検索ではない。公開ページの範囲指定 `1-50?re=1` は空の応答だった。

返信内の名前リンクには `hi=&key=...&date=...&wc=...` がある。これに `ｽｯﾌﾟ -Q8ld` を指定するとHTTP 200だが「ID検索エラー／しばらくしてからアクセスし直してください」。エラーを検索0件と扱わず、この経路への試行を止めた。調査スクリプトに日時・スレキー付き完全一致経路と、本文中の検索エラーで停止する処理を追加。

### Sdff-Q8ldの実データ照合

完全一致が12件を返す同じAndroid板で、Shift_JISの回線名を残した `ｽｯﾌﾟ *-Q8ld` と `ｽｯﾌﾟ Sdff-*` も比較。ともにHTTP 200だが「IDが見つかりませんでした」でレスヘッダー0件。アスタリスクは、この公開検索経路では目的の部分一致として機能しなかった。応答は `kyodemo-sdff-wildcard-last.html`／`kyodemo-sdff-wildcard-first.html` に保存。

Android板 `1792102288/10` の `ｽｯﾌﾟ Sdff-Q8ld` は完全一致検索で12件のレスヘッダーを返す。`SearchKyodemoFour.Page` と `TOKEN` で保存応答を解析し、12件とも前半 `Sdff`・後半 `Q8ld` を抽出できた。一方、`/sdemo/r/android/1792102288/10` はHTTP 200だが「スレッドを表示する(外部サイト)」のみで、対象ワッチョイを含まなかった。レス番号指定も候補取得の問題を解消しない。

4桁照合の成功は全体検索成功の証拠ではない。完全なワッチョイを事前に指定する検索では、未知の前半／後半を持つ投稿を発見できない。低速収集試作の実行は1ページに限定し、該当0件・再実行時のネットワーク通信0件を確認したが、ChMateへの組み込みは未実施。

### 再開後の確認

ユーザーが対象を特定：Android板 `1792102288/357`、2026-10-18 11:47:14.63、`ﾜｯﾁｮｲ bed4-6Zun`、`ID:HKq+ABFo0`。指定板でIDと完全ワッチョイはいずれもHTTP 200・該当なし、`-6Zun`と`bed4-`はHTTP 400。保存済みKyodemoスレページは297レス・取得日2026-10-17 23:26:58で、357レスを含む新しい状態ではない。収録遅延の可能性があり、この例を部分一致検証の陽性対照には使えない。完全一致で6件返るnetidolの対照結果とは分けて扱う。

ユーザー提供の `ID:HKq+ABFo0` をAndroid板で検索したが、HTTP 200「IDが見つかりませんでした」。`+` は `%2B` として送信済み。板が指定されていないため、別板での存在・不存在は判断できない。スレURLが得られれば、その板と日時を基準に調査する。

低速収集は未取得投稿の段階的な検索に役立つ可能性があるが、全体を検索できる索引の代替としての規模と網羅性が未解決。10秒に1ページなら1万ページだけでも約27.8時間、10万ページで約11.6日必要になる（通信時間・停止・ページ追加を除く理論下限）。複数ユーザーの合計負荷は端末単体の間隔制限だけでは制御できない。収集済み範囲しか検索できない実装を「Kyodemo全体検索」とは表記しない。

### 存在する投稿を使った対照検証

2026-10-18、netidol板で `ﾜｯﾁｮｲ b7e9-cwxD` は投稿を返した。同じ板・同じ値から前半または後半を省略した次の問い合わせを比較した。

| 条件 | 応答 |
| --- | --- |
| 完全な `ﾜｯﾁｮｲ b7e9-cwxD` | HTTP 200、該当スレ・レスあり |
| `-cwxD` | HTTP 400、検索条件拒否 |
| `b7e9-` | HTTP 400、検索条件拒否 |
| `ﾜｯﾁｮｲ -cwxD`（Shift_JIS） | HTTP 200、IDが見つかりませんでした |
| `ﾜｯﾁｮｲ b7e9-`（Shift_JIS） | HTTP 200、IDが見つかりませんでした |

証拠は `build/verification/kyodemo-20261018-131424/`、`kyodemo-known-suffix.html`、`kyodemo-known-prefix.html` に保存。回線名を補ってHTTP 200にする方法は、部分一致を実現しない。公開ページと共通スクリプトから全体部分検索の経路は発見できていない。

現時点の実装阻害要因は、全体を部分一致検索できる検索サービス／索引が利用できないこと。全板・全スレを端末ごとに収集して検索する方法は、低負荷という要件を満たさず、本文非掲載ページも補えない。実装再開には運営側が提供・許諾する検索APIまたは全体索引、あるいは動作する公開検索URLが必要。サイトへの問い合わせ送信は実施していない。

2026-10-18追加確認：Android板の `1792102288` と `1792061711` は、公開スレURLを取得してもレス本文・投稿者名がなく「スレッドを表示する(外部サイト)」へのリンクのみ。`r-head` が1件あるため、従来の調査スクリプトは誤って投稿取得成功に分類していた。現在は `external-link-only` と区別する。エッヂの `1792291793` では37個のレスヘッダーを確認したが、このページから実在するワッチョイの対照例は得られなかった。

これは全体クロールで解決できるという仮説に反する証拠であり、サイト内に本文を返さない板について全投稿検索を保証できない。公開検索インデックスまたはサイト運営側の対応が必要になる可能性がある。既存NG機能や手元のログ検索を全体検索の代用として完了扱いにしない。
